# План: Playwright-версия return-pd (изолированный запуск)

Статус: черновик плана. Дата: см. git.

## 1. Цель

Запустить рассылку обращений об отзыве ПД через **Playwright-управляемый браузер**,
полностью изолированный от основных браузеров пользователя:

- никаких Tampermonkey и ручной установки скрипта;
- собственный профиль браузера (userDataDir) — куки и сессии Яндекс-аккаунта
  живут только в нём, основной Chrome/Safari не затрагивается ни на чтение,
  ни на запись;
- запуск одной командой (`npm run pw:run`), headless-совместимость;
- сохраняются инварианты безопасности текущей версии: без авто-ретраев,
  стоп на первой ошибке, статусы `uncertain`/`rejected`, receipt до клика.

## 2. Что уже готово к переиспользованию (итог анализа кода)

Код уже разделён на слои, что делает миграцию инкрементальной:

| Слой | Модули | Судьба в Playwright-версии |
|---|---|---|
| Чистая логика | `types.ts`, `letters.ts`, `queue.ts` (класс `Queue`, `Transport`-интерфейс) | **переиспользуется как есть** — не зависят от DOM/GM |
| DOM-автоматизация Яндекса | `adapters.ts`, `yandex-account.ts`, `yandex-recipients.ts`, `mail-body.ts`, `send-letter.ts`, `yandex-send-response.ts` (~1500 строк) | портируется на Playwright-локаторы (селекторы те же, API другой) |
| UI-панель | `ui.ts`, `ui-surface.ts`, `launcher.ts` (~1000 строк) | заменяется CLI-конфигом (форма/галочки не нужны в headless) |
| Хранилище GM | `transport.ts` (store), `profile-storage.ts`, `gm.d.ts` | заменяется file-store (JSON в профиле проекта) |

Ключевой шов — интерфейс
`Transport { prepare(letter, signal, progress?) }` (`queue.ts`): достаточно
реализовать `PlaywrightTransport`, и вся очередь, статусы и антидублирование
логики работают без изменений.

## 3. Изоляция: как достигается

1. **`launchPersistentContext`** с `userDataDir: <project>/.pw-profile/yandex`
   (в `.gitignore`). Playwright хранит там куки/LocalStorage/кэш — это отдельный
   профиль, физически не пересекающийся с `~/Library/Application Support/Google/Chrome`.
2. **Встроенный Chromium из Playwright** (`npx playwright install chromium`),
   не системный Chrome. Двойная изоляция: ни профиль, ни бинарник пользователя
   не используются.
3. Никаких `storageState`/чтения кук пользователя; логин — один раз руками в
   headed-режиме, сессия персистится в userDataDir.
4. Запуск только по явной команде; никаких фоновых процессов.

## 4. Две стратегии

### Стратегия A — инъекция готового бандла (быстрый старт, 1–2 дня)
Playwright открывает Яндекс Почту в изолированном контексте и инжектит
`dist/return-pd.user.js` через `page.addInitScript`, подложив шимы GM_* API
(файловый стор через `page.exposeFunction`). Панель работает как раньше,
пользователь кликает в ней как обычно, но уже в изолированном браузере.

- Плюсы: почти ноль изменений в src; мгновенная проверка изоляции и
  антибот-поведения Яндекса; все существующие тесты остаются в силе.
- Минусы: UI остаётся ручным; headless всё равно требует человеко-кликов.

**Роль в плане: этап-валидатор.** Если Яндекс блокирует Playwright-Chromium —
узнаём это за часы, а не за недели портирования.

### Стратегия B — нативный порт (целевая, ~1–2 недели)
`PlaywrightTransport` реализует `Transport`; Yandex-модули портируются с
raw-DOM API на Playwright-локаторы; панель заменяется JSON-конфигом + CLI.

**Рекомендация: B — цель, A — обязательный первый этап.**

## 5. Этапы (Strategy B, с A как Этапом 1)

### Этап 0 — инфраструктура
- `npm i -D @playwright/test` + `npx playwright install chromium`
- `.gitignore`: `.pw-profile/`, `.pw-state/`
- Скелет `pw/` каталога (Node-код, не входит в userscript-бандл):
  ```
  pw/
    context.ts      # launchPersistentContext, launch options, инъекция шимов
    gm-shim.ts      # эмуляция GM_* в странице (для этапа A)
    file-store.ts   # JSON-стор: receipts, profile, очередь (замена GM_getValue…)
    config.ts       # загрузка/валидация pd-config.json
    transport.ts    # PlaywrightTransport (этап 2)
    yandex/         # портированные yandex-recipients, send-letter, …
    run.ts          # CLI-раннер
    login.ts        # headed-логин один раз
  ```
- Скрипты: `pw:login`, `pw:run`, `pw:dry`

### Этап 1 — инъекция (Strategy A)
- `pw/login.ts`: headed, `https://mail.yandex.ru`, ждём логина (проверка
  `identifyAccount`-подобным probe), профиль сохраняется сам.
- `pw/gm-shim.ts`: `GM_getValue/GM_setValue/GM_deleteValue/GM_listValues`
  через `exposeFunction('__pdStore', …)` → `file-store.ts`. Остальные гранты
  (`GM_registerMenuCommand`, `GM_setClipboard`, `unsafeWindow`) — no-op шимы.
- `pw/run.ts`: открыть почту → `addInitScript(бандл + шим)` → отдать управление
  пользователю (панель «Обращения по ПД» появляется сама).
- **Гейт перехода дальше**: 5+ писем успешно отправлены через инъекцию,
  антибот Яндекса не сработал, изоляция подтверждена.

### Этап 2 — PlaywrightTransport
- `pw/transport.ts`: `prepare()` = последовательность портированных шагов:
  открыть композер → `fillLetter`-эквивалент → при `deliveryMode: send` —
  клик с тем же receipt-протоколом (пишем receipt в file-store ДО клика).
- Перенос семантики `guard()`/abort: Playwright-версия использует
  `AbortController` + `signal` в `page.waitFor*` опциях — маппинг 1:1.
- `currentMailContext`/`matchesMailContext` заменяются проверкой URL контекста
  (в Playwright контекст стабильнее — SPA-навигация не рвёт его).

### Этап 3 — порт Yandex-модулей (~1500 строк → pw/yandex/)
Порядок по зависимостям:
1. `yandex-account.ts` (96 стр.) — определение аккаунта → probe-функция.
2. `mail-body.ts` (168) — запись тела → `locator.fill`/`evaluate` с тем же
   selection-механизмом.
3. `yandex-recipients.ts` (231) — ввод адреса, выбор из дропдауна,
   `yandexHasPendingRecipient` → `expect(locator)` с таймаутами из сигнала.
4. `send-letter.ts` (378) — поиск кнопки «Отправить» (те же селекторы и проверки
   однозначности), клик, ожидание тоста.
5. `yandex-send-response.ts` (264) — перехват ответа: вместо мутации fetch
  в странице — `page.on('response')` (чистее и надёжнее, чем DOM-хук).
- Правило порта: **селекторы и строки сообщений не меняются** — меняется только
  API доступа (`document.querySelector` → `page.locator`). Это упрощает
  сверку поведения и переиспользование фикстур.

### Этап 4 — конфиг и CLI вместо UI
- `pd-config.json` (gitignored, пример — `pd-config.example.json`):
  ```json
  {
    "profile": { "fio": "…", "email": "…" },
    "deliveryMode": "send",       // "draft" для dry-run
    "companyIds": ["…"],           // или "all": true
    "mode": "withdrawal",          // "withdrawal" | "inquiry"
    "delayMs": { "min": 20000, "max": 60000 }  // NEW: рандомная пауза между письмами
  }
  ```
- Валидация — переиспользуется `validateProfile` из `letters.ts`.
- `pw:run` печатает план рассылки (N писем, список компаний) и просит явное
  подтверждение `y/N` перед стартом; `--dry` = режим draft без подтверждения.
- Результат: лог-файл `.pw-state/run-<timestamp>.json` (статусы items как в UI)
  + скриншот карточки письма при ошибке.

### Этап 5 — поведение и антибот
- Пауза между письмами (см. delayMs) — сейчас очередь шлёт подряд; для
  Playwright-режима добавляем обязательный джиттер (в userscript не трогаем).
- Headed-режим по умолчанию первые N запусков; headless — флаг `--headless`.
- Человекоподобные тайминги: `locator.click({ delay })`, `page.waitForTimeout`
  с рандомом — аккуратно, без переусложнения.
- Если Яндекс банит: варианты — `channel: 'chrome'` с отдельным бинарником
  (НЕ профиль пользователя), `playwright-extra` + stealth. Решение откладываем
  до факта блокировки.

### Этап 6 — тесты
- Юнит-тесты `letters`/`queue` уже работают без изменений.
- Новые: `file-store` (receipt-протокол), `config` (валидация).
- E2E: smoke-тест `pw/transport` на фикстуре-странице (локальный HTML-макет
  композера Яндекса, переиспользуя подход `mail-editor-fixture.ts`); полный
  e2e против живой почты — ручной чек-лист, не в CI.
- `npm run check` остаётся главным гейтом; playwright-тесты — отдельный
  `npm run pw:test`, не ломающий существующий `pretest`.

## 6. Инварианты безопасности (переносятся, не изобретаются)

1. Receipt пишется до клика «Отправить» и переживает краш — теперь в
   `file-store`, тот же `RECEIPT_PREFIX`/`TTL`.
2. `uncertain` без подтверждения → запрет повтора, ручная проверка «Отправленных».
3. Стоп очереди на первой ошибке; `attempted`/`rejected` семантика сохраняется.
4. Ошибки Яндекса — с оригинальными кодами (`yandex-send-response`).
5. НОВОЕ для Playwright: перед стартом — интерактивное подтверждение плана
   рассылки; режим `draft` как безопасный прогон; лог каждого письма.
6. Изоляция профиля — см. §3; логин только руками, никаких учетных данных
   в коде/конфиг-примерах.

## 7. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Антибот Яндекса против Playwright-Chromium | средняя | Этап 1 выявит рано; fallback: channel:'chrome', stealth, headed |
| Дрейф DOM Яндекса (тот же, что у юзерскрипта) | постоянная | селекторы не меняем при порте → фикс одним местом |
| Сессия протухает между запусками | низкая | `pw:login` повторно; health-check аккаунта в начале run |
| Случайная отправка дважды при краше mid-run | низкая | receipt-протокол уже решает; + `--resume` только по явным статусам |

## 8. Definition of Done (по этапам)

- **Этап 1**: `npm run pw:login` + `npm run pw:run` → панель работает,
  5 писем отправлены в изолированном браузере, куки основного Chrome не тронуты
  (проверить: новый логин не требуется в основном браузере).
- **Этап 2–3**: `npm run pw:run -- --dry` готовит черновики всех писем
  без UI-панели.
- **Этап 4–5**: `npm run pw:run` с подтверждением отправляет выбранные письма,
  лог и статусы в `.pw-state/`, паузы между письмами соблюдаются.
- **Этап 6**: `npm run check` зелёный, `npm run pw:test` зелёный.
